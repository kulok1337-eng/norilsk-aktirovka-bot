# Бот актировок Норильска

Телеграм-бот, который следит за двумя сайтами и публикует в канал **опубликованное**
решение об актировках по районам Норильска. Бот не рассчитывает актировку по погоде:
он передаёт то, что официально опубликовано.

- Официальный источник: <https://норильск.рф/weather/>
- Резерв: <https://sgnorilsk.ru/pogoda/>
- Часовой пояс: Норильск, UTC+7 (без перехода на летнее время)
- Python 3.11/3.12, зависимости: `requests`, `beautifulsoup4`

## Что бот делает

1. Раз в 15 минут с 05:00 до 14:59 по Норильску (в остальное время — раз в час)
   скачивает обе страницы.
2. Ищет блок «ИНФОРМАЦИЯ ОБ АКТИРОВКАХ», дату, смену и таблицу по четырём
   районам: Центральный, Оганер, Талнах, Кайеркан.
3. Публикует сводку только если дата решения совпадает с сегодняшней по Норильску.
   Старые данные не публикуются.
4. При изменении решения той же даты и смены отправляет пост «Уточнение».
5. Официальный сайт имеет приоритет. Если официальное решение уже опубликовано,
   резерв не может его переписать.
6. При поломке разметки, незнакомом статусе или неполной таблице ничего не
   публикует и пишет предупреждение администратору в личку.

## Состав проекта

| Файл | Назначение |
| --- | --- |
| `main.py` | цикл проверки, состояние в SQLite, публикация в Telegram |

| `parser.py` | загрузка страниц, разбор, отпечаток решения, текст поста |
| `get_ids.py` | разовый помощник для получения ID канала и лички |

| `requirements.txt` | зависимости |

Присланный набор не запускался: `parser.py` и `config.py` были от разных версий.
Конкретно:

1. `config.py` не содержал `DISTRICTS`, хотя `parser.py` делал
   `from config import DISTRICTS` → `ImportError` при старте.
2. `main.py` импортировал `fingerprint` и `format_report`, которых в `parser.py`
   не было → `ImportError` при старте.
3. `test_parser.py` проверял поведение, которого в `parser.py` не было:
   неоднозначную дату, белый список статусов, обязательный маркер конца блока,
   повторный заголовок. Все 8 тестов падали.
4. Файл с именем `download (1)` — это не код, а текст `.gitignore`.
5. `get_ids.py` и `requirements.txt` были корректны и сохранены.

В этой версии `parser.py`, `config.py` и `main.py` согласованы, а все проверки
из `test_parser.py` действительно реализованы.

## 1. Создание бота в BotFather

1. Откройте @BotFather, отправьте `/newbot`.
2. Задайте название, затем username, заканчивающийся на `bot`
   (например, `norilsk_aktirovka_bot`).
3. Скопируйте токен. Он показывается один раз.
4. Токен храните **только** в переменных хостинга. Не вставляйте его в код,
   README, GitHub или чаты. Если токен утёк — `/revoke` в BotFather.
5. Откройте личку со своим ботом и нажмите «Старт»: без этого бот не сможет
   присылать вам уведомления.

## 2. Подготовка канала

1. Создайте канал (публичный или частный).
2. Добавьте бота администратором и включите право «Публикация сообщений».
3. Для публичного канала `CHANNEL_ID` — это `@username` канала, не ссылка
   и не название.
4. Для частного канала нужен числовой ID вида `-100...` (см. раздел 4).

## 3. GitHub

1. Создайте репозиторий, например `norilsk-aktirovka-bot`.
2. Загрузите файлы **в корень** репозитория: `main.py`, `config.py`,
   `parser.py`, `requirements.txt`, `README.md`, тесты, `fixtures/`.
   Не загружайте ZIP вместо исходников и не создавайте лишнюю вложенную папку.
3. Точные имена важны: `main.py`, `config.py`, `parser.py`.
4. Скрытый `.gitignore` при загрузке через веб иногда теряется. Если его нет,
   создайте файл `.gitignore` с содержимым:

   ```
   .env
   data/
   __pycache__/
   *.pyc
   ```

5. Убедитесь, что токена нет в истории коммитов.

## 4. Как узнать ID

Если ID неизвестны:

1. В переменных хостинга задайте только `BOT_TOKEN`.
2. Временно сделайте главным файлом `get_ids.py` (команда `python get_ids.py`).
3. Запустите проект.
4. Напишите боту в личку. Для ID частного канала добавьте бота администратором
   и опубликуйте новый пост.
5. В логах появятся ID лички и канала с названиями.
6. Остановите помощник и **верните главным файлом `main.py`**.

ID лички — это `ADMIN_ID`, ID канала — `CHANNEL_ID`. Не запускайте `get_ids.py`
одновременно с `main.py`: оба получают обновления одного бота. Если у бота
включён webhook, помощник завершится, ничего не меняя.

## 5. BotHost

Названия полей зависят от панели, но порядок такой:

1. Создайте Python-проект (рекомендуется Python 3.11/3.12).
2. Подключите GitHub-репозиторий и ветку `main` (или свою).
3. Главный файл: `main.py`. Если поле требует команду — `python main.py`.
4. Установка зависимостей: `pip install -r requirements.txt`
   (или подключите `requirements.txt` в панели).
5. Для private-репозитория дайте сервису доступ.
6. Задайте переменные окружения без кавычек:

| Переменная | Обязательна | Значение |
| --- | --- | --- |
| `BOT_TOKEN` | да | токен BotFather |
| `CHANNEL_ID` | да | `@username` или числовой ID канала |
| `ADMIN_ID` | да | ваш числовой ID |
| `DRY_RUN` | нет | `true` — тест в личку, `false` — публикация в канал |
| `DAY_INTERVAL` | нет | интервал днём, секунды, по умолчанию `900` |
| `NIGHT_INTERVAL` | нет | интервал ночью, секунды, по умолчанию `3600` |
| `ACTIVE_FROM` | нет | начало активного окна, час по Норильску, по умолчанию `5` |
| `ACTIVE_TO` | нет | конец окна (не включая), по умолчанию `15` |
| `DATA_DIR` | нет | каталог для `state.sqlite3`, по умолчанию `./data` |

7. Если хостинг уже подставляет `BOT_TOKEN` из отдельного поля, не задавайте
   второй экземпляр переменной.
8. Если на хостинге есть постоянное хранилище, укажите его реальный путь в
   `DATA_DIR`. Без постоянного хранилища база может исчезнуть при пересборке:
   бот продолжит работать, но возможен повторный пост.
9. Запускайте **один** экземпляр `main.py`. Два процесса будут дублировать посты.
10. В комплекте есть `Dockerfile`. Если панель умеет собирать образ по нему,
    она сама поставит Python 3.12 и зависимости. Если не умеет — файл просто
    игнорируется, настройте проект вручную, как описано выше.

## 6. Тестовый запуск

1. Оставьте `DRY_RUN=true`.
2. Запустите проект. В логах должно быть:
   `Бот @... запущен. DRY_RUN=True` и путь к базе.
3. В личку придёт уведомление о запуске.
4. Если сегодняшнее решение уже опубликовано, придёт сводка с пометкой
   `ТЕСТ — в канал не отправлено`. Проверьте дату, смену и районы на сайте.
5. Если решения на сегодня нет, сводки не будет — это нормально, смотрите логи.
6. Бот не отвечает на `/start`: команды ему не нужны.

## 7. Публикация в канал

1. Поставьте `DRY_RUN=false` и перезапустите проект.
2. При старте бот проверит, что `CHANNEL_ID` — канал, а бот — администратор
   с правом публикации.
3. Сегодняшнее решение придёт в канал, даже если раньше приходило в тесте:
   история теста и канала хранится раздельно.
4. Изменение той же даты и смены придёт отдельным постом «Уточнение».

## 8. Расписание

- 05:00–14:59 по Норильску — раз в 15 минут (`DAY_INTERVAL=900`).
- В остальное время — раз в час (`NIGHT_INTERVAL=3600`).
- Первая проверка — сразу после запуска.
- Для 30 минут днём задайте `DAY_INTERVAL=1800`.
- Ночью бот не публикует устаревшие данные и не будит администратора
  сообщениями о пропуске даты.

## 9. Проверка кода

Установите зависимости и запустите тесты:

```bash
pip install -r requirements.txt
python -m unittest -v
```

Ожидается 20 успешных тестов:

- 8 тестов `test_parser.py` — логика разбора и защита от неоднозначностей;
- 6 тестов `test_real_pages.py` — фрагменты реальных страниц, кодировка,
  формат поста, отпечаток;
- 6 тестов `test_main_flow.py` — публикация, дедупликация, «Уточнение»,
  тестовый режим, приоритет официального источника, сохранение состояния.

Тесты не заменяют первый запуск на хостинге: они проверяют сохранённые
фрагменты страниц, а не сегодняшнюю разметку сайтов.

## 10. Ограничения и важные предупреждения

- Бот передаёт опубликованное решение, а не прогноз и не расчёт по погоде.
- Резервный сайт «Северный город» часто обновляется с задержкой. Его старые
  данные молча игнорируются; уведомление о пропуске даты приходит только по
  официальному источнику и только после 08:00, чтобы не засорять личку.
- Если разметка сайта изменится, публикации не будет, а администратор получит
  сообщение с причиной. Это сделано специально: лучше пропуск, чем ложная
  «актировка».
- Незнакомый статус (не «нет» и не диапазон классов) останавливает публикацию.
- Если сайт отдаёт сертификат, которого нет в хранилище `requests`, бот один раз
  повторяет запрос без проверки TLS и пишет предупреждение в лог. Это компромисс
  для российских госсайтов; по возможности установите корневой сертификат.
- При сбое между отправкой в Telegram и записью базы технически возможен дубль.
- Если страница уже заменена решением на вторую смену, утреннее решение первой
  смены восстановить нельзя.
- Уведомления одного типа ограничены одним разом в 6 часов.
- Бот не хранит переписку и не имеет команд — только публикация и служебные
  сообщения администратору.

## 11. Частые ошибки

| Симптом | Причина и решение |
| --- | --- |
| `Unauthorized` | неверный или отозванный `BOT_TOKEN` |
| `chat not found` | неверный ID, бот не добавлен в канал или вы не нажали «Старт» |
| `Forbidden` | бот заблокирован или нет доступа к каналу |
| «У бота нет прав администратора» | включите право публикации в канале |
| `No module named requests` / `bs4` | не установлен `requirements.txt` |
| `No module named config` / `parser` | файлы не в корне проекта или неверные имена |
| «Пропуск даты» | сегодняшнего решения нет — это намеренный пропуск |
| «Не найден заголовок…» / «Неизвестный статус…» | изменилась разметка сайта, нужна адаптация `parser.py` |
| После изменения GitHub ничего не поменялось | пересоберите проект, если автодеплой не настроен |
| Посты дублируются | запущено два экземпляра или потеряна база в `DATA_DIR` |

## 12. Если хостинг пишет «Сборка Docker образа не завершена»

Это сообщение означает: хостинг не смог упаковать проект в контейнер, поэтому
контейнера нет и запускать нечего. Токен, BotFather и логика бота здесь ни при
чём — ошибка происходит **до** запуска бота.

Проверьте по порядку:

1. **Файлы в корне репозитория.** В корне GitHub должны лежать именно
   `main.py`, `config.py`, `parser.py`, `requirements.txt`. Не `main (1).py`,
   не `main.py.txt`, не `requirements (1).txt` и не папка с проектом внутри
   репозитория.
2. **Ветка.** В панели указана та же ветка, что в GitHub: `main` или `master`.
3. **Доступ.** Если репозиторий приватный, у хостинга должен быть доступ к нему.
4. **Главный файл.** В поле «главный файл» — `main.py`, команда — `python main.py`.
5. **Python.** 3.11 или 3.12. В комплекте есть `Dockerfile` с Python 3.12.
6. **Лог сборки.** Откройте его в админ-панели и найдите последнюю красную
   строку:
   - `requirements.txt: No such file or directory` — файл не в корне или назван
     иначе;
   - `Could not find a version that satisfies the requirement` — зависимость
     не скачалась (сеть/зеркало хостинга);
   - `repository not found` / `Authentication failed` — нет доступа к GitHub;
   - `main.py: not found` — неверный главный файл или лишняя папка;
   - `python:3.12-slim: not found` — хостинг не может скачать базовый образ.

После исправления нажмите «Пересобрать». Ошибка «контейнер не найден» — это
следствие неудачной сборки, отдельно её лечить не нужно.

## 13. Безопасность

- Токен и ID храните только в переменных хостинга.
- `.gitignore` исключает `.env`, `data/`, `__pycache__/`.
- При утечке токена сразу отзовите его в BotFather и выпустите новый.
- Не публикуйте дампы базы: в ней служебные ключи, но не сам токен.
